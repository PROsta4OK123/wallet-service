# Wallet Service

Транзакційний сервіс гаманців на Java 21, Spring Boot і PostgreSQL. Він підтримує поповнення, списання, перекази та платежі за графіком фінансування.

У фінансовому сервісі мало просто записати новий баланс у таблицю. Треба пережити повторний запит клієнта, два одночасні списання й запуск кількох планувальників. Ці сценарії закриті транзакціями, блокуваннями та обмеженнями PostgreSQL. Кожну зміну балансу можна звірити з журналом проводок.

## Що реалізовано

- два етапи життєвого циклу платежу: спочатку створити, потім підтвердити;
- створення гаманця з нульовим або заданим початковим балансом;
- поповнення, списання та переказ між гаманцями;
- захист від від’ємного балансу та подвійного підтвердження;
- ідемпотентне створення платежів через `Idempotency-Key`;
- незмінний журнал проводок `wallet_entry` і звірка балансу;
- заявки на фінансування, графік, ручне й автоматичне створення платежу;
- безпечна паралельна робота кількох екземплярів планувальника;
- пагінація за курсором без глибокого `OFFSET` і зайвого `COUNT(*)`;
- метрики Prometheus, перевірка стану, `X-Request-Id`, OpenAPI та Swagger UI;
- інтеграційні й конкурентні тести на PostgreSQL через Testcontainers.

## Архітектура

Застосунок побудовано як модульний моноліт за бізнес-можливостями:

```text
com.example.wallet
├── wallet   - баланс і конкурентний доступ до гаманців
├── payment  - життєвий цикл платежу, підтвердження та проводки
├── funding  - заявки, графік і фоновий планувальник
└── shared   - конфігурація, помилки та наскрізні механізми
```

Залежності всередині модулів спрямовані від `api` до `application`, а далі до `domain` та `infrastructure`. ArchUnit стежить за межами: контролер не звертається до репозиторію напряму, а домен не залежить від web-фреймворку.

PostgreSQL відповідає за цілісність даних. Статус платежу, баланс, проводки та прогрес заявки змінюються в одній транзакції. Під конкурентним навантаженням працюють такі правила:

- платіж блокується перед підтвердженням;
- гаманці блокуються в стабільному порядку UUID, що знижує ризик взаємного блокування;
- незалежні гаманці обробляються паралельно;
- `CHECK`, foreign key та unique constraints залишаються останньою лінією захисту;
- планувальники забирають різні порції задач через `FOR UPDATE SKIP LOCKED`;
- тимчасове закріплення задачі дозволяє іншому процесу продовжити роботу після збою;
- HTTP-запити та фонові задачі працюють на virtual threads, а обмежений пул JDBC не дає перевантажити базу.

Детальний шлях проєктування, альтернативи та компроміси описані в [SOLUTION.md](SOLUTION.md).

Повна інструкція з підготовки Java, Maven, Docker і PostgreSQL лежить у [docs/ENVIRONMENT.md](docs/ENVIRONMENT.md).

## Швидкий запуск

Потрібні Java 21 або новіша, Maven 3.9 або новіший і Docker.

Застосунок разом із PostgreSQL запускається однією командою:

```bash
docker compose up --build
```

Після старту API доступне на `http://localhost:8080`, а база опублікована на порту `5433`, щоб не конфліктувати з локальним PostgreSQL на стандартному `5432`.

Для локальної розробки можна підняти лише базу, а застосунок запустити через Maven:

```bash
docker compose up -d postgres
mvn spring-boot:run
```

## Корисні адреси

- Swagger UI - `http://localhost:8080/swagger-ui.html`;
- OpenAPI JSON - `http://localhost:8080/v3/api-docs`;
- стан сервісу - `http://localhost:8080/actuator/health`;
- метрики Prometheus - `http://localhost:8080/actuator/prometheus`;
- звірка журналу - `http://localhost:8080/actuator/ledgerReconciliation`.

## Перевірка

Для інтеграційних тестів Docker має бути запущений, оскільки Testcontainers створює справжній екземпляр PostgreSQL:

```bash
mvn test
```

Набір тестів перевіряє міграції, архітектурні межі, конкурентний захист від overdraft, одночасні запити з одним idempotency key, повторне підтвердження, lease планувальника та звірку балансу з журналом.

Після запуску сервісу можна виконати k6-сценарій:

```bash
k6 run scripts/load-test.js
```

Сценарій створює та підтверджує платежі зі сталою інтенсивністю, а потім показує p95 часу підтвердження. Результат залежить від CPU, диска, Docker і налаштувань PostgreSQL, тому готових цифр у репозиторії немає.

## Приклади API

Створити порожній гаманець або гаманець із початковим балансом:

```bash
curl -X POST http://localhost:8080/api/v1/wallets \
  -H "Content-Type: application/json" \
  -d '{"openingBalance":1000.00}'
```

Поле `openingBalance` необов’язкове й за замовчуванням дорівнює нулю. Ідентифікатор генерує сервер, а початкова сума враховується в reconciliation як початковий баланс, а не як платіж.

Отримати гаманець:

```bash
curl http://localhost:8080/api/v1/wallets/10000000-0000-0000-0000-000000000001
```

Створити переказ. `Idempotency-Key` не обов’язковий, але рекомендований для production-клієнтів:

```bash
curl -X POST http://localhost:8080/api/v1/payments/transfers \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: transfer-demo-1" \
  -d '{"sourceWalletId":"10000000-0000-0000-0000-000000000001","targetWalletId":"10000000-0000-0000-0000-000000000002","amount":125.00}'
```

Підтвердити створений платіж:

```bash
curl -X POST http://localhost:8080/api/v1/payments/{paymentId}/confirm
```

Повторення створення з тим самим ключем і payload поверне первинний платіж. Повторне використання ключа з іншим payload завершиться `409 Conflict`.

Поповнення та списання проходять той самий двоетапний шлях:

```bash
curl -X POST http://localhost:8080/api/v1/payments/deposits \
  -H "Content-Type: application/json" \
  -d '{"walletId":"10000000-0000-0000-0000-000000000001","amount":50.00}'

curl -X POST http://localhost:8080/api/v1/payments/withdrawals \
  -H "Content-Type: application/json" \
  -d '{"walletId":"10000000-0000-0000-0000-000000000001","amount":10.00}'
```

Переглянути заявку, створити платіж за пунктом графіка раніше строку або призупинити заявку:

```bash
curl "http://localhost:8080/api/v1/funding-requests/20000000-0000-0000-0000-000000000001?size=50"

curl -X POST http://localhost:8080/api/v1/funding-requests/20000000-0000-0000-0000-000000000001/schedule-items/30000000-0000-0000-0000-000000000002/payment

curl -X POST http://localhost:8080/api/v1/funding-requests/20000000-0000-0000-0000-000000000001/suspend
```

Графік повертається за cursor pagination. Якщо `cursor.hasNext` дорівнює `true`, наступний запит має передати обидва значення курсора:

```text
?afterDate=2026-11-23&afterId=30000000-0000-0000-0000-000000000001&size=50
```

Такий підхід не виконує дорогий `COUNT(*)` і не деградує на глибоких сторінках, як `OFFSET`.

## Контракт помилок і трасування

Помилки повертаються як `application/problem+json` і містять стабільний бізнес-код. Кожна HTTP-відповідь має `X-Request-Id`; це саме значення потрапляє в лог і тіло помилки, тому запит можна простежити без логування чутливого request body.

## Конфігурація

Локальні значення з `application.properties` можна перевизначити змінними Spring:

- `SPRING_DATASOURCE_URL`;
- `SPRING_DATASOURCE_USERNAME`;
- `SPRING_DATASOURCE_PASSWORD`;
- `SPRING_DATASOURCE_HIKARI_MAXIMUM_POOL_SIZE`.

Для планувальника доступні `FUNDING_SCHEDULER_ENABLED`, `FUNDING_SCHEDULER_DELAY` і `FUNDING_SCHEDULER_BATCH_SIZE`.
